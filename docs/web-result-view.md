# Web Result View

Web 结果区当前采用三层信息结构，目标是在不打断现有简约风格的前提下，把“看卦”从纯文本提升为可扫描的结构化阅读体验。

## 设计目标

- 先看结构，再读文本
- 让动爻变化一眼可见
- 保持桌面与移动端都可读
- 不额外引入前端框架或复杂状态
- 与现有 FastAPI + Jinja 模板架构保持一致

## 信息结构

结果区分为三层：

1. 标题区
- 当前本卦编号与名称
- 进入会话详情页的入口

2. 卦象区
- 本卦卦象卡片
- 变卦卦象卡片
- 互卦卦象卡片
- 本卦到变卦的逐爻对照卡片

3. 文本区
- 白话摘要
- 卦辞 / 彖 / 象
- 已翻译时优先展示英文爻辞 / 小象
- 动爻取用规则
- 选中爻文本

## 对照视图

“本卦 -> 变卦”卡片采用逐爻对照，而不是把两幅图完全并排重复展示。

每一行包含：

- 爻位编号
- 本卦该爻
- 变化指示符
- 变卦该爻

只有发生变化的爻位会高亮，未变化的爻位保持中性背景。

这样做的原因：

- 用户真正关心的是“哪一爻变了”
- 直接并排两组六爻时，变化信息需要人工比对，认知成本高
- 逐爻对照更适合移动端纵向阅读

## 视觉规则

- 阳爻：整条实线
- 阴爻：中间断开的两段线
- 动爻：使用轻量高亮描边
- 老阳：`o`
- 老阴：`x`
- 逐爻对照中的变动行：整行淡色背景强调

## 为什么不做成前端交互组件

当前没有引入额外前端运行时，原因是：

- 数据已经由服务端完整生成
- Jinja 模板足够表达当前结果视图
- 现阶段更重要的是稳定结构和可读性，而不是客户端动画

这让页面更容易测试，也更容易在 CLI / API / Web 之间保持信息一致。

## 后续扩展

后续如果继续增强 Web 结果区，建议按这个顺序推进：

1. 增加动爻前后文字解释联动
2. 增加“推演步骤”展开区，显示本卦 / 互卦 / 变卦的生成过程
3. 为不同起卦法增加方法专属结果卡片
4. 增加分页支持，方便浏览大量历史会话
